# 事件循环后端设计:libuv、io_uring 与自研的边界

这是一篇**纯讨论文档**(先文档后实现,不附代码),回答一个问题:luna 的异步 IO 底座,停在 libuv 就够了吗?io_uring 要不要现在接?Windows 的 IOCP 要不要自己碰?

**结论先行**:IOCP 无需自研——libuv 在 Windows 上就是 IOCP,这是"白送"的;io_uring 列为 P2 观察项,只有当 profile 证明 epoll 成为瓶颈时才启动;阶段一的全部精力放在把 libuv 单后端做稳。下面每个判断给出理由。

## 一、现状:libuv 单后端,三大平台一次拿全

luna 已有 opt-in 的事件循环:`loop` 模块(b12e50f)提供 Node 命名的 timer/immediate 与 `run`/`stop`,随后 `loop.fs`(1a3691d)把 `readFile`/`writeFile`/`stat` 放上 libuv 线程池,回调落回循环线程。锁定的 libuv 是 1.44.2(`deps/libuv`,静态链接,单二进制不变)。

关键事实是 libuv 的后端映射:**Windows 上是 IOCP,Linux 上是 epoll,macOS/BSD 上是 kqueue**,同一套 API 自动分发。这意味着:

- luna 今天在 Windows 上的异步文件与套接字 IO,底层已经走在 IOCP 上——**"IOCP 无需自研"不是权衡结论,是既成事实**;
- 自研 IOCP 封装(注册重叠 IO、完成端口排队、取消语义、`WSARecv` 的零字节读技巧)要重新踩 libuv 踩过十几年的坑,换来的只有"少一层抽象"——而这一层抽象正是我们买 libuv 时想买的东西;
- 三平台的**行为一致性**由 libuv 负责(比如 `uv_fs_*` 在各平台统一走线程池语义),自研封装则要逐平台证明等价。

所以现状这一节的判断只有一句:**libuv 单后端已经覆盖三大内核的事件机制,任何"再接一个后端"的提议都必须先回答 libuv 缺了什么。**

## 二、io_uring:为什么不现在接

io_uring 是 Linux 5.1 起的原生异步 IO 接口:用户态与内核共享一对环形缓冲区,提交/收获批量化,理论吞吐与 syscall 开销都优于 epoll。它**值得评估**,但结论是"现在不接",理由分三层。

### 2.1 libuv 主线的实际采用状况

我们的锁定版本 1.44.2 完全没有 io_uring 代码;上游主线从 1.45.0 起**仅在文件 IO 上**引入 io_uring(替代部分线程池路径),且因沙箱环境的兼容事故调整为默认关闭、需 `UV_USE_IO_URING=1` 显式开启;**网络 IO 主线至今仍走 epoll**。这条事实链说明两件事:

- 连 libuv 这样维护了十几年的项目,接入 io_uring 也采取了"单领域、可回退、默认关"的保守姿势——这不是保守过度,是 io_uring 的现实(见 2.3);
- "接 io_uring"在 luna 里**不能通过升级 libuv 免费获得**(网络面),它只能是一个独立的第二后端工程。

### 2.2 收益评估:luna 的负载形状够不到瓶颈

io_uring 的收益集中在**海量并发连接 + 高频小 IO**的场景——每秒数十万请求的代理、存储引擎、消息队列。luna 的定位是 REPL 与脚本运行时:

- `loop.fs` 已经把文件 IO 移到线程池,主线程本来就不在等磁盘;
- 典型脚本的并发量级是"几十个句柄",epoll 在这个量级的 syscall 开销是微秒级噪音;
- REPL 交互路径(attach、补全)走的是 unix socket + 计数钩子,与 IO 后端无关。

**没有 profile 数据证明 epoll 是瓶颈,就没有接 io_uring 的收益侧理由。**这也是"P2 观察项"的含义:不是"永远不做",而是"由数据触发,不由技术热情触发"。

### 2.3 维护成本与风险

- **内核门槛**:io_uring 的能力随内核版本漂移(5.1 基础可用,缓冲注册、multishot、`IORING_OP_*` 扩展散布在 5.19/6.x),CI runner 与用户机器的内核版本差异会把"特性检测"变成常态负担;
- **沙箱封禁**:大量容器环境以 seccomp 禁用 io_uring(Google 因安全考虑在生产与 Android 全面禁用),调用失败要逐 API 回退到 epoll——**回退路径就是第二个后端,写一个后端的钱一分不少花**;
- **实现纪律**:若做,**必须用 liburing**(io_uring 作者维护的官方用户态库),**禁止手写 syscall 封装**——io_uring 的 ABI 演进快、语义细(提交顺序、取消、注册缓冲的生命周期),手写封装等于与内核 ABI 赛跑,这正是"找成熟库、不自己写"铁律的适用场景。

## 三、分层抽象:如果将来要第二后端,怎么摆

**接口层**(现在就值):`loop` 已是统一门面,面向 Lua 的四个面——**timer**(setTimeout/setInterval)、**fs**(loop.fs 三件套)、**net**(将来的 TCP/unix 套接字)、**signal**(^C 已经由 prepare 钩子承接,将来的 TERM/HUP)。真正要做的是把 `luna_loop.c` 内部拆出一层后端接口——句柄创建/取消、`prepare`/`check` 钩子(attach 轮询与 ^C 接在这上面)、就绪分发的最小 C 接口,libuv 实现为唯一后端。这层拆分**不引入新依赖、不改行为**,纯粹让"后端"成为一个可替换的名词。

**多后端切换**(P2 才值):后端以编译期选择(opt-in)进入,默认仍是 libuv。切换的真实代价不在 happy path,而在边界语义的逐条复刻:

- 错误映射(libuv 的 `uv_strerror` 字符串契约已被 `loop.fs` 测试钉死);
- 句柄计数与 `run` 的"跑到空"语义(prepare 常驻句柄会让循环永不空退,这类坑每个后端各踩一遍);
- 信号与 net 面的接入(libuv 的 `uv_signal`/`uv_poll` 并非 1:1 映射到 io_uring,重叠部分仍需 epoll 兜底)。

所以方案是:**接口先行、单实现、测试钉边界;第二后端只有在收益侧(2.2)有数据、成本侧(2.3)接受封禁回退时才立项。**

## 四、三后端对比

| 维度 | epoll(经 libuv) | IOCP(经 libuv) | io_uring(经 liburing) |
| --- | --- | --- | --- |
| 就绪/完成模型 | 就绪通知,fd 就绪后读 | 完成通知,重叠 IO | 完成通知,共享环形队列 |
| luna 现状 | Linux 在用,1.44.2 | Windows 已在用(白送) | 未接 |
| 需要写代码吗 | 否 | **否** | 是:整条独立后端 + epoll 回退 |
| 收益场景 | 常规并发,足够 | 同左 | 数十万并发连接/高频小 IO |
| 内核/系统门槛 | 全版本 Linux | Windows 全版本 | Linux ≥5.1,完整特性 5.19+ |
| 沙箱兼容 | 无障碍 | 无障碍 | 常被 seccomp 禁用,须回退 |
| 实现纪律 | — | — | 只许 liburing,禁手写 syscall |
| 维护方 | libuv 上游 | libuv 上游 | luna 自己(第二后端) |
| 结论 | **保持** | **保持,零动作** | **P2 观察项,数据触发** |

## 五、结论与路线

1. **阶段一(现在)**:libuv 单后端做稳——`loop`/`loop.fs` 的语义由测试钉死;`luna_loop.c` 内部整理出后端接口(纯重构、零行为变化),让"多后端"从"重写"降级为"实现一个接口"。
2. **P2 观察项**:io_uring(liburing 绑定,禁止手写 syscall 封装)。启动条件写死:profile 证明 epoll 在真实脚本负载上是瓶颈。未满足条件前,任何 io_uring 工作量都是负资产。
3. **IOCP**:不设事项。它已经在 libuv 里,这就是结论。
